# Shared repository instructions

This is the canonical project guidance for coding agents working in this repository.
Claude Code loads this file directly; Codex loads `AGENTS.md`, which instructs it to read and follow this file before starting repository work.

## Repository purpose

This repository holds **Drain Vision Pod**, a 천안시(Cheonan) 빗물받이(storm drain) blockage detection + dredging-priority prediction system proposed for a competition/demo with a **1박 2일 (overnight) build window**. `Drain_Vision_Pod_기획안_v2.md` is the authoritative planning document (spec, architecture, presentation script); `backend/`, `frontend/`, `edge/`, `db/` are the working MVP implementation built directly from that plan's section 9. When code and plan disagree, treat the plan as intent and the code as the current best-effort realization of it — update whichever is stale.

## Structure

- `Drain_Vision_Pod_기획안_v2.md` — the plan: problem framing, architecture, hardware BOM, data pipeline, DB schema, API spec, dev order, organized into numbered sections (1. 프로젝트 개요 → 9. 프로젝트 구성/기술 스택). Section 9 (9.1–9.6) is the technical spec the code below implements.
- `backend/` — FastAPI + SQLAlchemy + Pydantic server (`main.py`, `models.py`, `schemas.py`, `forecast.py`). Uses SQLite (`backend/drainvision.db`, git-ignored/generated), auto-created from `db/init.sql` on first startup.
- `db/init.sql` — schema only (vehicles/drains/detections/system_events + indexes). Source of truth for the DB shape; `backend/models.py` mirrors it.
- `db/drains_seed.json` — the demo seed data (`vehicles` plus a `drains` array with lat/lng/route_ids[]/elevation/is_flood_zone). Shared physical drains carry multiple `route_ids`, so different vehicles can observe the same `drain_id`. This is the **only** place demo drain coordinates live — `backend/main.py` reads it once on first startup (when `drainvision.db` doesn't exist yet) to populate `vehicles`/`drains`/`drain_routes`. To add a drain, append an entry here, delete `backend/drainvision.db`, and restart the backend — no code changes needed anywhere.
- `backend/.env` (git-ignored/local, not committed) — `KMA_API_KEY`, `SILENCE_GRACE_SECONDS`, `SAFEMAP_API_KEY` (행안부 생활안전지도 침수흔적도, `backend/flood.py` — field names in the API response are unconfirmed, see that file's docstring); loaded via `python-dotenv` at the top of `main.py` before any module that reads these at import time. `backend/.env.example` documents the keys; copy it to `.env` and fill in real values.
- `frontend/` — Vite + React dashboard (status cards, Leaflet map, priority list, priority-reasons breakdown, route planner, per-vehicle drain lookup, history panel). Large lists use shared client-side pagination (`components/Pagination.jsx`): status cards 6/page, vehicles 6/page, and priority/history/per-vehicle drain lists 8/page; a selected drain is kept visible when live updates reorder the data. Connects to `/ws/dashboard` for live updates, falling back to 1s `GET /api/drains` polling (with auto-reconnect) if the socket drops. The map uses live OpenStreetMap tiles (`react-leaflet`) — this is a deliberate exception to the plan's "no external network dependency" stance (기획안 7장), traded off because a recognizable real map was worth it; tile images need network, but markers/clicks/data keep working if tiles fail to load, so the dashboard doesn't break offline, it just shows a blank basemap.
- `edge/` — Pod-side pipeline (`infer.py`, `gps_match.py`, `sender.py`, `run.py`, `weights/drain_v5_best.pt`). Runs standalone against the backend over HTTP; has no dependency on a real Pi/camera/GPS (see Architecture below).
- No linter/formatter/test suite is configured in any of the three codebases — verification is manual (run the servers, hit the endpoints, check the DOM), matching the project's 1박2일 scope.

## Commands

Backend (from repo root):
```
pip install -r backend/requirements.txt
uvicorn main:app --reload --app-dir backend        # http://localhost:8000
```

Frontend:
```
cd frontend
npm install
npm run dev      # http://localhost:5173 (VITE_API_BASE in .env points at the backend, default http://localhost:8000)
npm run build     # production bundle -> frontend/dist
```

Edge Pod (simulator mode — no hardware required; from `edge/`):
```
pip install -r requirements.txt
python run.py --simulate --loops 5 --interval 0.3   # cycles GPS through Drain A→B→C and POSTs detections to the backend
```
`run.py --help` lists the real-hardware flags (`--source video:<path>|webcam:<index>|picamera2`, `--gps serial:<port>`, `--model <yolov8n-seg .pt path>`) that replace the simulator pieces once camera/GPS/fine-tuned weights exist — see Architecture below.

Manually trigger the forecast-driven priority recompute (what the frontend's "우선순위 재계산" button calls):
```
curl -X POST http://localhost:8000/api/priority/refresh
```

Manually trigger a multi-team route recommendation (what the frontend's route planner panel calls):
```
curl -X POST http://localhost:8000/api/route/plan -H "Content-Type: application/json" -d '{"team_count": 2}'
```

Manually force the weather mode for a demo (what the frontend's 평소/비 예보/폭우 예보/자동 buttons call — see the weather-mode bullet below):
```
curl -X POST http://localhost:8000/api/weather/mode -H "Content-Type: application/json" -d '{"mode": "HEAVY_RAIN"}'   # NORMAL | RAIN | HEAVY_RAIN | AUTO
```

`SILENCE_GRACE_SECONDS` (env var, default 10) controls how long the backend waits after close-range telemetry before appending a `RESULT_MISSING` system event if no detection arrived. It never creates or changes a drain assessment.

There is no top-level script that starts all three at once — run backend, then frontend and/or edge against it, in separate terminals/processes.

## Architecture — how the three codebases fit together

The system is three independent processes that only talk over the HTTP/JSON contract defined in `backend/main.py` + `backend/schemas.py` — there is no shared code between `edge/`, `backend/`, and `frontend/`. Understanding one file in isolation won't explain the data flow; the contract is what matters:

- **Edge → Backend (detections)**: `edge/run.py` composes `infer.py` (frame → status/occlusion_pct/confidence, from a YOLO11n-seg model trained on two classes — `drain_area` the currently-visible unobstructed grate, `drain_full` the whole physical drain outline; `infer.compute_occlusion(area_px, full_px) = 1 - area_px/full_px`, computed entirely within one frame — no per-drain external baseline. If only `drain_full` is detected (visible area is completely gone), occlusion is forced to 100%; if only `drain_area` is detected (no evidence anything is hidden), occlusion is 0%; if neither is detected, the frame is unassessable) and `gps_match.py` (GPS coord → nearest `drain_id`, restricted to the drains sharing the Pod's `VEHICLE_ROUTE_ID` — see 기획안 2.1) *before* sending. `DrainMatcher.match()` rejects (`None`) a candidate farther than `--match-radius-m` (default 30m, `gps_match.DEFAULT_MAX_MATCH_DISTANCE_M`) away. The resolved `drain_id` is part of the POST body (`POST /api/detections`), not re-derived server-side — the backend trusts the edge's matching and just persists it. `gps_match.py` fetches its candidate drain list from `GET /api/drains` once at startup rather than owning its own copy; `--simulate` mode's fake GPS trace (`SimulateGPS`) also cycles through those same fetched candidates, so it never goes stale relative to `db/drains_seed.json`.
- **Edge visit aggregation (not per-frame)**: inference runs for every frame, but object detection may return no drain mask. That outcome is `UNASSESSABLE` with `reason_code="DRAIN_NOT_DETECTED"` and `occlusion_pct=None`; it means the physical state cannot be assessed, not that inference was skipped or full blockage was measured. `aggregate_visit()` ignores unassessable frames when measurable frames exist and returns final `UNASSESSABLE` only when every frame in the visit lacks a drain mask. Measurable frames use IQR removal, confidence weighting, and majority status (BLOCKED > OCCLUDED > CLEAR on ties — BLOCKED is the more severe class, occlusion_pct >= `infer.OCCLUDED_MAX_PCT` (60%); v2.13 fix, previously inverted).
- **Edge → Backend (telemetry + system event)**: `run.py` sends telemetry every loop. Close-range telemetry starts a debounced silence timer; if no visit detection arrives before it expires, the backend appends `RESULT_MISSING` to `system_events`. This is a device/network/pipeline event, never a drain status, and it does not touch `drains` or `detections`. `GET /api/system-events?drain_id=` exposes it separately; the detail panel renders a separate “시스템 이벤트” section. Keep the grace period longer than the realistic visit-flush and POST latency.
- **Backend state**: `drains` holds the current physical snapshot; `detections` is the append-only assessment log; `system_events` holds operational events such as `RESULT_MISSING`; `vehicles` resolves identity. A `POST /api/detections` inserts an assessment, updates the drain snapshot, and recomputes priority. Startup migration renames legacy `UNDETECTED` rows to `UNASSESSABLE` with `DRAIN_NOT_DETECTED`, and moves legacy `UNCHECKED` rows into `system_events` without deleting/resetting the database.
- **priority_score formula + reasons** (`backend/forecast.py::compute_priority_breakdown`, implements 기획안 2.2절 v2.6 개정): `w1*elevation_risk + w2*flood_history_flag + w3*staleness_risk + w4*occlusion_norm` — 4 components now, weights looked up from `forecast.WEIGHT_PROFILES[weather_mode]` (`NORMAL: (0,0,0.15,0.85)`, `RAIN`/`HEAVY_RAIN: (0.15,0.25,0.15,0.45)`), where `weather_mode` is the system-wide state described below. `staleness_risk` (`forecast.staleness_risk(last_updated, now, weather_mode)`) is a *weather-independent* 0.15 slice in every mode — it ramps linearly from 0 (just checked) to 1.0 at `forecast.STALENESS_THRESHOLD_DAYS[weather_mode]` days since `last_updated` and caps there (never checked → always 1.0). The threshold itself *is* weather-dependent (`NORMAL: 14, RAIN: 7, HEAVY_RAIN: 1`) — "폭우 전엔 무조건 점검" is approximated as "not checked in the last 24h counts as maximally overdue". The reason text for staleness uses the *actual* uncapped elapsed days (computed separately from the capped risk value) — an earlier version derived the displayed day-count by reversing the capped risk, which silently under-reported elapsed time past the threshold; don't reintroduce that. `elevation_risk` is a min-max normalization *across all drains currently in the table*, so it shifts whenever a drain is added/removed — it is not a fixed per-drain constant. The breakdown function also emits `priority_reasons` (guarded per-component by `if w > 0`, so a zero-weighted factor never shows up as a "reason" even though its raw value is still stored) — human-readable Korean strings sorted by contribution descending. The frontend's "우선순위 근거" panel (`PriorityReasons.jsx`) renders both the reasons and all 4 raw metric values with their *current* weight annotated (`×0.15` etc.) and zero-weight metrics visually grayed out (`weightProfile` prop, sourced from `weatherAlert.weight_profile`) — this exists specifically so a metric with a nonzero raw value but zero active weight (e.g. 고도 위험도 in NORMAL mode) doesn't look like it's silently being ignored. Score + 4 normalized components + reasons are persisted as columns on `drains` (not recomputed on read).
- **City-wide weather mode (3-tier, not per-drain)** (`backend/forecast.py::fetch_tomorrow_weather`/`classify_weather_mode`, `backend/main.py::refresh_weather_alert`): implements 기획안 2.2-2절 (v2.5) — splits the old single boolean alert into two independent mechanisms sharing one classification: a **gate** (which drains even qualify for today's action list) and an **order** (the weight profile above). `POST /api/priority/refresh` queries the KMA short-term forecast **once** for Cheonan city hall (`CHEONAN_CITY_HALL_LAT/LNG`), extracting POP (rain probability) and every hourly PCP category value for tomorrow via `_hourly_pcp_by_time`. `classify_weather_mode(pop, pcp_3h_mm)` trusts the 3-hour rolling PCP sum when computable (`>=60mm → HEAVY_RAIN`, `>0mm or POP>=40 → RAIN`, else `NORMAL`) and only falls back to POP-only thresholds (`RAIN_POP_THRESHOLD=40`, `HEAVY_RAIN_POP_THRESHOLD=70`) when it can't be computed — because POP alone can't distinguish "high chance of drizzle" from "lower chance of a downpour". The 60mm figure (`forecast.HEAVY_RAIN_PCP_3H_MM`, v2.11) is KMA's real 호우주의보(heavy rain advisory) threshold (3-hour cumulative ≥60mm, or 12-hour ≥110mm) — the point where KMA itself starts using "호우"(heavy rain) terminology, which matches this system's "폭우 예보" label far better than the much rarer "극한호우"(extreme heavy rain, hourly ≥50mm) tier tried briefly in v2.10 and reverted for being too rare to fire in practice. Since the short-term forecast API's PCP field is hourly-only, `forecast._max_rolling_3h_pcp()` builds a real 3-hour cumulative by summing every genuinely-consecutive triplet of hourly values (`_hourly_pcp_by_time`) and taking the max across the day — not a single-hour proxy — so it's directly comparable to the official 3-hour criterion; it returns `None` (triggering the POP-only fallback) if fewer than 3 consecutive hourly slots are available. `pcp_mm` (single max hourly value) is still returned/stored as a display-only reference figure and is not what gates the mode. The resulting mode drives `forecast.OCCLUSION_ACTION_THRESHOLD[mode]` (70/50/40%), which `plan_route`'s default candidate filter uses instead of the old flat `priority_score >= 0.3` cutoff. **Ordering matters**: `refresh_priority` calls `refresh_weather_alert()` *before* looping over drains, specifically so `recalc_priority_for_drain` reads the just-updated `weather_alert_state["mode"]` rather than a stale one — this bit ordering backward once during development and silently computed every drain's score one refresh cycle behind. State lives in an in-memory `weather_alert_state` dict (not a DB table — resets on restart, acceptable at demo scope) and broadcasts over `/ws/dashboard` as `{"type": "weather_alert", ...}`, distinct from the drain-shaped broadcasts `App.jsx`'s `ingest()` handles — `ws.onmessage` branches on `payload.type === "weather_alert"` before falling through to `ingest()`. The loud amber banner (`weatherAlert.active`) is reserved for HEAVY_RAIN only; NORMAL/RAIN show only the small always-visible mode+threshold indicator (`.weather-mode-row`) so banner fatigue stays low.
- **Manual weather-mode override, for demos** (`POST /api/weather/mode`, v2.9): real KMA data won't reliably produce all three modes on demand during a live presentation, so this endpoint lets a presenter force `weather_alert_state["mode"]` directly — bypassing `fetch_tomorrow_weather()` — and immediately recomputes every drain's `priority_score` the same way `POST /api/priority/refresh` does, so the effect is visibly instant rather than waiting for the next poll cycle. `main.py::_apply_weather_mode()` is the shared helper both `refresh_weather_alert()` (real data) and `set_weather_mode()` (manual) call to fill in the mode-derived fields (`occlusion_threshold`, `staleness_threshold_days`, `weight_profile`, banner `message`) — keep them sharing this helper rather than duplicating the field-setting logic if either changes. Setting any concrete mode (`NORMAL`/`RAIN`/`HEAVY_RAIN`) sets `weather_alert_state["manual_override"] = True`, which makes `refresh_weather_alert()` a no-op (it returns before touching state) — this is deliberate: otherwise clicking "우선순위 재계산" mid-demo would silently kick the forced mode back to whatever the real forecast says. Sending `mode: "AUTO"` clears the override and re-fetches real weather immediately. The manual message text is tagged `[데모 수동 전환]` in the banner so it's never confused with a real forecast alert. Frontend (v2.10 UI revision): `App.jsx`'s `.weather-mode-row` has two buttons — `수동` (toggles `manualPanelOpen`, revealing a `<select className="mode-select">` with the three concrete modes; `onChange` calls `handleSetMode()` immediately, no separate "apply" step) and `자동(실제 예보)` (calls `handleSetMode('AUTO')` and closes the dropdown). A `useEffect` on `weatherAlert?.manual_override` force-opens the dropdown whenever the backend reports a manual mode is active — so if another browser tab or a WS broadcast turns manual mode on, this tab's dropdown appears too instead of silently disagreeing with the banner. `setWeatherMode()` (`api.js`) response is written straight into `weatherAlert` state; the currently-active button/select value is derived from `weatherAlert.manual_override` + `weatherAlert.mode` (not separate local state). Drain score updates arrive via the existing `/ws/dashboard` broadcast (this endpoint broadcasts both the drain list and the `weather_alert` message), not from this call's own response.
- **Drains ↔ routes is many-to-many**: a `drain_routes` join table (not a `route_id` column on `drains`) backs `Drain.route_ids` (a `@property` on the ORM model reading the eager-loaded `routes` relationship, `lazy="joined"`). A single drain can legitimately sit on more than one operational route (e.g. a garbage-truck route and a bus route covering the same street) — `edge/gps_match.py::DrainMatcher` checks `vehicle_route_id in (d.get("route_ids") or [])`, not equality. `Vehicle.route_id` stays a single column (a vehicle drives one route at a time); only drains needed the multiplicity.
- **Elevation lookup** (`backend/elevation.py::fetch_elevation(lat, lng)`, `GET /api/elevation?lat=&lng=`): 기획안 2.2절 names 국토지리정보원 DEM as the intended source, but its point-lookup API spec couldn't be confirmed reliably, so this calls the public, keyless Open-Elevation API (SRTM-based) instead — consistent with the plan's "공개 자료 기반" principle even though it's not the exact named agency. Returns `None`/502 on failure rather than a dummy fallback (unlike the KMA/YOLO fallback pattern below) because this is an occasional manual lookup used to fill in `drains_seed.json`, not something the live detection loop depends on every cycle.
- **Per-vehicle drain lookup** (`GET /api/vehicles`, `GET /api/vehicles/{id}/drains`): the second endpoint walks that vehicle's detections, keeps the latest row per `drain_id` plus a count, and joins static drain info. System events are never mixed into this list. Frontend vehicle selection filters the map and clicking a drain drives shared detail selection.
- **Action gate + route planning** (`backend/main.py::needs_action`, `backend/routing.py`, `POST /api/route/plan`): `needs_action` is shared by the priority list and route candidates. It includes never-checked, `UNASSESSABLE`, weather-threshold occlusion, or stale drains; a valid human resolve suppresses all but staleness. `RESULT_MISSING` does not directly change the physical-state gate. Geographic clustering (k-means) assigns candidates to teams; within a team, visit order is decided purely by distance (nearest-neighbor construction + alternating 2-opt/or-opt local search, `routing.py::geo_route`) — priority score only decides gating/ranking elsewhere, not in-team order, since an earlier "highest-priority fixed first stop" version could force a long detour when that point was geographically isolated (2-opt alone couldn't undo it; fixed in v2.12 by dropping the anchor and adding or-opt). OSRM/haversine fallback remain as documented in code.
- **Human maintenance actions ("조치 완료"/"점검 완료")** (`POST /api/drains/{id}/resolve`, v2.8, C9): lets a person record physical handling of BLOCKED/OCCLUDED, never-checked, or UNASSESSABLE drains without replacing the AI result. It only sets maintenance metadata. `is_resolved()` and `last_checked_at()` keep the existing staleness-clock behavior; `MaintenanceAction.jsx` mirrors the backend resolve check.
- **`confidence` feeds visit aggregation, nowhere else** (`edge/run.py::aggregate_visit`): a visit's final `occlusion_pct` is a confidence-weighted average of the kept (non-outlier) readings, not a plain mean — frames the detector was less sure about pull the result less. Falls back to a plain mean only if every kept reading has `confidence == 0` (guards a division by zero, not a realistic case with real weights). `confidence` itself (the averaged value sent to the backend) is still just descriptive metadata on `detections` — nothing server-side reads it back out.
- **Backend ↔ Frontend**: no shared types — the frontend (`src/format.js`, `src/api.js`) hand-matches the JSON shape returned by `GET /api/drains`/`GET /api/drains/{id}/history`/`POST /api/route/plan`. If you change a field name in `backend/schemas.py`, grep the frontend for that field before assuming the UI still works. The frontend's only WS peer is the backend (the Pod never opens a WebSocket — it only POSTs detections + telemetry). `App.jsx` opens `/ws/dashboard` on mount and merges every broadcast (single drain from a detection/inferred-occlusion, or the full list from a priority refresh) into local state via `ingest()`; if the socket closes it starts 1s `GET /api/drains` polling as a fallback and retries the WS connection with exponential backoff (1s→8s), dropping back to WS-only once it reopens. `ingest()` merges by spreading whatever keys arrive, so new backend fields flow through without any frontend merge-logic changes.
- **"No hardware yet" fallback pattern, used in two places** — `backend/forecast.py` provides deterministic dummy weather when KMA is unavailable; `edge/infer.py` provides deterministic CLEAR/BLOCKED/OCCLUDED/UNASSESSABLE output when weights are unavailable.
- **Adding demo data**: `db/drains_seed.json` contains coordinates, vehicles, `detections`, and separate `system_events`. Detection rows initialize snapshots; system events never do. The backend reads this file only when creating a new database. `db/init.sql` only defines schema.

## Document conventions to preserve when editing

- **Revision log at the top**: the file opens with a blockquote (`>`) summarizing each revision (v2, v2.1, v2.2, …). When making a substantive change, append a new `> vX.Y 개정 요약: ...` line rather than rewriting or deleting prior ones — the log is meant to show the plan's evolution to reviewers.
- **Cross-references over duplication**: sections reference each other by number (e.g., "2.3절 참조", "9.3절과 연결") instead of restating content. Keep new additions consistent with this — link to the authoritative section rather than copying it.
- **Honesty about limitations is a deliberate strategy, not a gap to fix**: the plan repeatedly and intentionally surfaces its own weaknesses (e.g., GPS matching error, baseline occlusion-% drift under real vehicle mounting, budget-driven hardware tradeoffs) and defends them explicitly rather than hiding them — often with a suggested presentation script line. When revising, keep this "acknowledge the limitation, then explain why it doesn't undermine the core value" pattern rather than deleting caveats to make the plan look stronger than it is.
- **No fabricated numbers**: the team has explicitly chosen not to commit to concrete fleet-size / rollout-count figures for the vehicle-based expansion strategy (section 2.3) — do not add specific vehicle counts or timelines there unless the user provides them.
- **Scope discipline**: the plan explicitly excludes direct coordination with Cheonan city departments (design is based entirely on public data — 공공데이터포털, UPIS, 환경부 자료) due to the short build window. Don't introduce assumptions that depend on unconfirmed department data (e.g., pipe flow capacity) without flagging them as roadmap items, matching the existing pattern in section 8.
- **Language**: the document is written entirely in Korean; keep edits in Korean and preserve existing technical terms (e.g., class names CLEAR/BLOCKED/OCCLUDED, table/column names) exactly as defined in sections 2–3 and 9.3 rather than re-translating them.
